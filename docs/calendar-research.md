# Astrology and cultural-calendar engineering research

Research date: **2026-10-03 UTC**. Scope: browser-static calculators, transparent conventions, reusable engines, and independent validation fixtures. This is a bounded engineering catalogue, not an exhaustive survey of traditions. Six Exa searches requested 35 results; exact URLs were then fetched from upstream projects, standards authors, observatories, and calendar providers. Search results were deduplicated by URL and assessed against the primary documentation below. Popularity counts and cached package metadata are not proof of current maintenance.

Repository ownership, existing implementation, build measurements, and implementation status must be joined with the lead engineer's repository inventory. No application files were edited by this research workstream.

## Recommended architecture

Use one shared input model for an exact UTC instant, explicit IANA time zone or explicit offset, latitude in degrees north, longitude in degrees east, elevation in metres, calendar/date convention, and input certainty. Keep date-only civil dates distinct from instants. A calendar conversion should never accidentally shift a selected date because the user's device is in another zone. Use explicit time zones in all formatting.

Use Astronomy Engine for the application's shared Sun, Moon and planetary quantities. It is a browser-supported MIT implementation whose upstream accuracy target is one arcminute, validated upstream against NOVAS and JPL Horizons. This is an upstream target, not a new guarantee about this application's wrappers. Test the wrappers separately. Derive traditional divisions/aspects from those quantities, with each convention exposed. Do not imply that the library itself implements houses, ayanamshas, or religious calendars.

Use dedicated Adhan calculations for prayer times because the selectable religious conventions and high-latitude resolution are not reducible to one generic sunrise formula. Keep the same coordinate/time input contract and label this separate engine. Prefer native `Intl.DateTimeFormat` for a modest, clearly labeled civil-date conversion surface (Hebrew, Chinese, Buddhist, Indian national, Islamic variants), with an explicit runtime support check. It does not provide holiday policy, reverse conversion, astronomical boundaries, or universal religious authority.

Avoid introducing Swiss Ephemeris into the browser release without a deliberate licensing decision and an audited browser integration. Its numerical output can serve as an independently sourced reference. Do not change the whole application's license merely to add a feature. Hebcal similarly needs a GPL compatibility decision if bundled; its public converter is useful as an independent fixture source.

## Specific implementation cautions

### Astronomy / astrology

- `EclipticLongitude(body, date)` is a **heliocentric** longitude function. It is inappropriate as a direct natal-chart longitude API. For apparent geocentric longitude, the relevant composition is `Ecliptic(GeoVector(body, date, true)).elon`; verify each supported body and the library's light-time/aberration conventions. The Moon should be compared explicitly against external data.
- Natal longitudes are normally geocentric, whereas a live sky overlay requires observer/topocentric horizontal coordinates. Share an engine and input model without conflating these frames.
- A 12-sector equal-house wheel and a whole-sign wheel are different: equal cusps increment 30° from the ascendant; whole-sign house 1 begins at the selected zodiac sign's 0°. Neither implements Placidus.
- Unknown birth time must suppress angles/houses and mark all fast-moving quantities, especially the Moon, as approximate. A noon representative instant is acceptable only if it is visibly labeled and not presented as an exact natal chart.
- Retrograde means decreasing selected geocentric ecliptic longitude. Unwrap the finite difference across 360°; use a documented interval and report “near stationary” inside a tolerance. A comparison one day apart can miss exact station timing and should not be sold as a station predictor.
- Sidereal calculation is not simply subtracting “24°” for all years. Ayanamsha is epoch/method-dependent; nutation and precession conventions affect comparison. Do not expose menu options whose formulas are unimplemented.
- Panchang tithi index is `floor(normalize(moonLongitude - sunLongitude)/12)+1`; paksha divides the 30 tithis into 15+15. Ayanamsha cancels in elongation. Nakshatra divides sidereal lunar longitude into 27 equal sectors. Yoga divides the normalized sum of sidereal Sun and Moon longitudes into 27 sectors. Karana has 60 half-tithi intervals but **not** a simple 7-name cycle over all 60: fixed first/last karanas require special handling.
- Instant Panchang quantities do not establish observance dates. Local sunrise, amanta/purnimanta month convention, skipped/repeated tithi, regional holiday rules and day boundaries require separate validation.
- Interpretation text should say which traditional system it describes. No astronomical calculation validates guaranteed personal events or medical/financial outcomes.

### Time zones and dates

- Native `new Date('YYYY-MM-DDTHH:mm')` uses the device's zone. It is not a safe birth-date parser for a different location.
- A geographic point does not automatically identify a historical time zone. Offer IANA zone/explicit UTC offset input instead of inventing a longitude-based civil time zone. Current location's zone is not automatically the birth location's zone.
- Temporal's default `compatible` behavior silently chooses an offset. Prefer `reject` for a birth-time form, then ask the user to explicitly choose earlier/later for repeated times. A nonexistent time should be corrected, not silently shifted.
- Modern IANA zones provide historical data, but pre-1970 accuracy is uneven and civil conventions may not have existed. An honest initial tested date range such as 1900–2100 is preferable to claiming all dates that JS `Date` technically accepts. Range is a product validation decision, not the upstream ephemeris maximum.
- `Intl.DateTimeFormat` may silently fall back to another calendar. Check `resolvedOptions().calendar` matches the requested identifier. For Chinese dates, `formatToParts` can emit `relatedYear` and `yearName`, not just `year`; preserve leap-month names.
- Date-only conversion should use an explicit civil day and stable zone, for example noon UTC for a form that explicitly converts civil Gregorian dates. An instant conversion should honor the chosen IANA zone. Never mix these contracts.
- Hebrew/Islamic formatted civil-day values do not automatically implement sunset-to-sunset religious boundaries. State the boundary used; offer a separately calculated local-sunset interpretation only if it has been implemented and tested.

### Prayer times and Qibla

- Adhan uses Meeus-based astronomy with explicit presets. Muslim World League uses 18° Fajr / 17° Isha; ISNA/North America 15° / 15°; Karachi 18° / 18°; Egyptian 19.5° / 17.5°. Asr depends on Shafi/Hanafi setting. Never label these as one universal Islamic method.
- Umm al-Qura uses a 90-minute Isha interval; upstream explicitly notes adding 30 minutes during Ramadan. Do not auto-apply Ramadan adjustments from an unspecified Islamic calendar. Either implement the chosen convention or expose a visible manual adjustment.
- `PolarCircleResolution.Unresolved` is the upstream default. Preserve undefined/invalid values as “No calculable time with this method” rather than displaying midnight. Alternative nearby-date/location strategies must be opt-in, labeled approximations.
- High-latitude twilight choices include middle-of-night, one-seventh-night, and twilight-angle portions. A generic altitude-based root finder alone does not implement them.
- Qibla is an initial great-circle bearing toward the Kaaba, measured clockwise from true north. The device compass may be magnetic or uncalibrated. A numerical bearing is valid without sensors; do not imply camera alignment without sensor calibration. At the destination or an antipodal singularity the direction is undefined/unstable and needs an explicit unavailable state.

## Bounded research limitations and follow-up

The catalogue covers named needs without claiming all regional variants. Independent numerical prayer-time and house fixtures remain to be collected by implementation/QA. True Lahiri and other ayanamsha propagation must be independently evaluated over any promised date range; a single 2026 table match is insufficient. Jain, Sikh and complete Hindu/Buddhist observance modules need explicitly chosen community conventions and authoritative date tables. Chinese conversion should remain a tested civil-date conversion unless a complete ephemeris-based rule set is added. No research result here is proof that an application feature is working or deployed.
