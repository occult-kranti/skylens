# Globe aircraft data: access, coverage and implementation choices

Research date: **October 5, 2026, America/New_York (EDT, UTC−04:00)**. Official documentation and upstream source were inspected for the requested worldwide, zoomable flight globe. This is a bounded review of the providers below, not an exhaustive census of aircraft-data services. No new live aircraft endpoint requests were made by this research lane; earlier browser-delivery evidence is identified separately.

## Decision

A globe that users can rotate, pan and zoom anywhere in the world is feasible on GitHub Pages. It does **not** establish simultaneous worldwide live-aircraft coverage. Among the reviewed services, no documented, currently verified, permission-free anonymous **all-aircraft** feed was established for this deployment:

- AvioADSB and adsb.fi document all-network snapshots, but restrict them to contributors/feeders.
- The inspected adsb.lol public router and documentation do not expose `/v2/all`; direct readsb/raw aggregation is a feeder benefit.
- Airplanes.live's public guide lists filtered and nearby endpoints, not an unrestricted all-aircraft endpoint.
- OpenSky documents a global endpoint, but its current terms require a previous written agreement for operational use in a live product, even nonprofit use.

Implement worldwide **regional browsing** with a visible query circle, provider attribution, sample time, freshness and an explicit coverage label. A user can select a different region; one bounded nearby request covers that region. Do not fill unqueried countries with invented aircraft, display old regions as current without their timestamps, or tile the whole Earth with regional requests to recreate a restricted snapshot. A separately authorized all-network JSON endpoint may be supported as an advanced source without pretending a local receiver sees the whole planet.

Even an authorized provider's “all” means **all qualifying aircraft known to that network**, not every aircraft in the world. Receiver coverage, radio visibility, aircraft equipment, filtering and report freshness still limit the dataset. Camera overlays and satellite propagation remain separate from aircraft-feed coverage.

## What readsb and tar1090 actually provide

A separate AI source reviewer inspected the upstream implementations below; these are reproducible software contracts, not permission to access another operator's deployment.

| Component | Verified upstream contract and source |
|---|---|
| Capability discovery | `data/receiver.json` advertises `refresh` in milliseconds, `globeIndexGrid`, `globeIndexSpecialTiles`, `reapi`, `binCraft`, optional `zstd`. Generated by `generateReceiverJson()` in [readsb/json_out.c](https://github.com/wiedehopf/readsb/blob/dev/json_out.c). Receiver coordinates may also be present; avoid publishing them unintentionally. |
| Indexed globe data | tar1090's [html/script.js](https://github.com/wiedehopf/tar1090/blob/master/html/script.js) selects visible-region tiles: `data/globe_<index>.json`, `.binCraft` or `.binCraft.zst`; index padded to at least four digits. There is **no universal public `globe.json` endpoint** established by this source. A military-specific tile/request is not a general full-world route. |
| Viewport API | `re-api/?json&box=<south>,<north>,<west>,<east>` or `re-api/?binCraft&box=...`, optionally `&zstd`; selected objects can use `find_hex`. Notice this bounds order differs from AvioADSB's bbox order. It queries the data already available to that backend. |
| Backend requirements | [nginx-readsb-api.conf](https://github.com/wiedehopf/tar1090/blob/master/nginx-readsb-api.conf) proxies the frontend API route to readsb's Unix socket/local TCP API. Requires running receiver/aggregation software, `--tar1090-use-api` and `--net-api-port`. GitHub Pages cannot execute those services. |
| Ordinary JSON | [README-json.md](https://github.com/wiedehopf/readsb/blob/dev/README-json.md): `now` in Unix **seconds**, `aircraft` array. Indexed JSON also has `global_ac_count_withpos`, `globeIndex` and bounds. That count means positioned aircraft known to the backend, not every aircraft globally. Compatible v2 `ac` envelopes instead use millisecond `now`. |
| Binary data | The canonical browser decoder `wqi()` is in [tar1090/html/formatter.js](https://github.com/wiedehopf/tar1090/blob/master/html/formatter.js). binCraft has a header, millisecond timestamp, advertised record stride, counts, tile bounds, version and validity flags. Coordinates use millionths of a degree; current altitude slots use 25-foot units, track divided by 90 and age in tenths of seconds. Version branches include 20240218 and 20250403. Copying offsets without the version/validity logic is unsafe. |
| Cadence and history | [README-api.md](https://github.com/wiedehopf/readsb/blob/dev/README-api.md) and JSON documentation: `--write-json-every` controls generation/API cache refresh, default one second. tar1090 slows refresh according to payload, viewport, inactivity and device load, and limits concurrent tile loading. Optional traces live under `data/traces/<suffix>/trace_recent_<hex>.json`; archived paths under `globe_history/...` require backend recording. A one-second generation interval is not an all-aircraft accuracy/update guarantee. |

Software licences: [readsb GPL-3.0-or-later](https://github.com/wiedehopf/readsb/blob/dev/LICENSE), [tar1090 GPL-2.0-or-later](https://github.com/wiedehopf/tar1090/blob/master/LICENSE). Importing/distributing their code entails the applicable licence conditions. Consuming a documented JSON format does not require copying the renderer, nor grant rights to remote data, aircraft databases or map tiles. No binary decoder or full tar1090 code was imported as part of this research.

GitHub Pages can host the static globe, JSON fixtures and **clearly dated snapshots**. It can request a separately authorized HTTPS/CORS endpoint. It cannot operate a receiver daemon, collect a distributed ADS-B network, run the nginx proxy or conceal private provider/OAuth secrets. A single owner-operated receiver offers its local reception coverage; `--write-json-globe-index` partitions existing observations and does not create worldwide observations. HTTP cache policy, application snapshot time and per-aircraft position age are different; the inspected nginx proxy example is not a universal CDN-cache guarantee.

## Recommended integration boundary and acceptance

1. **Worldwide navigation, bounded source coverage.** Keep globe center/zoom separate from physical observer location. A globe search must not silently move the camera observer. Render the active coverage circle and provider age; show “unqueried” versus “no reports” distinctly. Use one explicit Load this area action for a regional request, cancel the old request and preserve the provider's minimum interval and quota.
2. **Optional authorized feed.** Require an explicitly configured HTTPS endpoint and format (`readsb aircraft.json` seconds/`aircraft`, or compatible v2 milliseconds/`ac`). Omit credentials, reject redirects, do not accept private keys in query strings or auto-discover LAN hosts. The endpoint owner must permit the Pages origin and the intended data use. Show its declared coverage and timestamp; a custom URL does not establish worldwide coverage.
3. **Bounded payload and rendering.** Validate response size/counts and finite fields; reject over-limit payloads explicitly instead of truncating them. Reuse aircraft normalisation, identity, age and geographic geometry rather than inventing a globe-specific ephemeris. Render at viewport cadence while fetching much more slowly. Avoid a label per aircraft at globe scale; selected/nearby objects get priority, with keyboard-accessible details.
4. **Freshness and provenance.** Position age is provider time minus per-position age, advanced with wall time; receipt time does not make a stale cache live. The globe retains reported geographic positions without extrapolation; the separate Sky overlay uses a capped motion estimate, not a recorded flight path. Distinguish sampled positions, inferred motion and historical snapshots. Keep altitude convention, source and range units consistent between globe, list and camera.
5. **Real release evidence.** Verify deep links under the Pages base path, zoom/pan/selection, world-wrap/polar limits, stale/error/empty states, cancellation, provider attribution and a fully offline globe with no false live markers. Fixture performance and browser mock success do not prove nonempty real provider coverage. Physical camera alignment remains a separate phone check.

The actionable first delivery is therefore a full navigable globe with honest regional aircraft data and an explicit authorized-feed extension point. A simultaneous live all-network dataset remains contingent on a suitable provider agreement/contribution or an owner-operated aggregation endpoint. No paid subscription, account, receiver infrastructure or agreement was created by this review, and no denied route was bypassed.
